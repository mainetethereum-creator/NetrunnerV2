# World graphics and performance audit — 2026-09-24

Scope: static source review of `/expedition`, `/metro`, the Hub, and the Sakura/canal/east Base scenery. This is an inventory of code costs, **not a measured FPS or GPU profile**. No scene was launched, no asset was rebuilt, and the owner's working tree and map/camera saves were left intact. The current tree contains concurrent edits, so line references describe the 2026-09-24 working tree.

## Transparency, LOD and resource ownership

- Sakura foliage and canal foliage use alpha test and opaque depth writes (`sakura-park.ts:41-43`, `canal.ts:37`), avoiding blended canopy sorting. Sakura fountain spray, petals, steam and pool glows use transparent materials (`sakura-park.ts:59,170-189`). Canal mist is a tiny 24-point transparent batch with frustum culling disabled (`canal.ts:112-114`). The actual overdraw contribution needs a GPU capture; source alone does not establish that it is dominant.
- Expedition decorative props have a 27–44 m screen-door fade and a 44 m skip; buildings and tree silhouettes are excluded (`components/expedition/distance-detail.ts:5-29`). Grass chunks, mobile density scaling and 10 Hz streaming are documented in `docs/expedition-runtime-budget.md`. Any reduction beyond these existing bounds needs measured evidence and side-by-side visual checks.
- Hub is React/CSS with replaceable image layers, not a WebGL scene (`src/ui/hub/HubApp.tsx:10-12`, `src/ui/hub/Hub.module.css:41-64`). It has CSS drop shadows on cards and PLAY (`Hub.module.css:251,256`); there is no continuous 3D render loop to optimize. Image decode/transfer and CSS paint are the relevant profiling questions.
- Async loaded Sakura, canal and east model prototypes are retained for shared geometry/material teardown, and each module has a disposed guard (`sakura-park.ts:18,33-35,222-225`; `canal.ts:18-29,128-132`; `east-district.ts:18,23-25,181-185`). Canal handles fulfilled promises after disposal. Expedition and Metro both stop loops, remove listeners, dispose scene trees/composers and renderer (`components/expedition/scene.ts:185`, `components/metro3d/scene.ts:90`). No definite retained-GPU-resource leak was identified from these paths. Confirm repeated route enter/exit with renderer memory and browser heap snapshots before claiming leak-free behavior.

## Profiling hypotheses and acceptance checks

These are questions, not observed regressions. In a foreground tab, capture representative stationary and walking frames at the same camera: Base Sakura/canal/east, Expedition dense authored district and vegetation, and Metro platform. Record main/shadow draw calls, triangles, GPU pass timings where supported, JS update time, texture and render-target memory, and sustained frame cadence. Separate mobile and desktop captures. `renderer.info` counters are useful but do not measure GPU time; `document.hidden` pauses or skips work on some routes.

Prioritize fixes only when the capture identifies a material cost. For shadow changes, compare contact, foliage and architecture shadows at the original camera. For batch splitting, check all editor transforms and instance colors. For light gating, inspect near/far seams and emissive night scenes. For point or transparency changes, compare fountain, rain, petals and canal mist from oblique and close views. Preserve the owner's saved Base map and camera throughout visual checks.
